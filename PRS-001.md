## 1. Abstract

PRS-001 defines a cryptographic rarity and provenance standard for digital assets.

It allows an NFT, artwork, model output, dataset, document, media file, or digital artifact to be anchored to a SHA-256 entropy hash, assigned a mathematically verifiable leading-zero rarity class, included in a public proof structure, and verified through a reproducible procedure.

The purpose of PRS-001 is to transform digital rarity from subjective metadata into independently verifiable cryptographic evidence.

---

## 2. Motivation

Most NFT rarity systems are based on assigned traits, collection metadata, marketplace perception, or creator-defined scarcity.

PRS-001 introduces a cryptographic rarity layer.

Instead of saying an asset is rare because a metadata trait says it is rare, PRS-001 allows an asset to be connected to a SHA-256 anchor whose rarity can be independently calculated.

A PRS-001 asset may therefore prove:

- the rarity of its entropy anchor,
- the probability class of that anchor,
- the inclusion of that anchor in a collection,
- the connection between the anchor and the asset metadata,
- and the public verification path for the artifact.

## 3. Core Claim

## 5. Minimum PRS-001 Asset Requirements

A valid PRS-001 asset should include:

1. an asset identifier,
2. an asset URI or metadata URI,
3. a SHA-256 anchor hash,
4. a leading-zero bit count,
5. a rarity class,
6. a proof object,
7. a Merkle leaf,
8. a collection root or standalone attestation,
9. and a verification procedure.

## 6. Rarity Basis

PRS-001 defines rarity by leading zero bits in a SHA-256 digest.

For a uniformly distributed SHA-256 digest, each additional leading zero bit makes the expected work approximately twice as difficult.

The expected rarity of a digest with `n` leading zero bits is:

    1 in 2^n

A digest with 40 leading zero bits has approximate odds of:

    1 in 2^40 = 1 in 1,099,511,627,776

A digest with 44 leading zero bits has approximate odds of:

    1 in 2^44 = 1 in 17,592,186,044,416

## 10. Merkle Leaf Construction

A PRS-001 Merkle leaf should be constructed from a deterministic representation of the proof object.

Recommended procedure:

1. Create the PRS-001 proof object.
2. Canonicalize the JSON.
3. Hash the canonical proof object using SHA-256.
4. Prefix the result as a Merkle leaf.

Example:

    merkle_leaf = SHA256(canonical_json(proof_object))

The exact canonicalization procedure should be defined in implementation documentation to avoid inconsistencies between verifiers.

---

## 11. Collection Root

The first PRS-001 release uses a single public collection root.

A collection root commits multiple PRS-001 proof objects into one Merkle tree.

The basic flow is:

    proof_object → merkle_leaf → merkle_proof → collection_root

This allows a verifier to confirm that:

1. the asset proof object is included in the collection,
2. the anchor hash is committed,
3. the rarity class is committed,
4. the metadata URI is committed,
5. and the published collection root matches the public attestation.

---

## 12. Public Verification Procedure

A PRS-001 verifier should be able to check:

1. the anchor hash is a valid SHA-256 digest,
2. the digest has the claimed number of leading zero bits,
3. the rarity class matches the leading-zero bit count,
4. the proof object matches the metadata commitment,
5. the Merkle leaf is correctly derived from the proof object,
6. the Merkle proof leads to the published collection root,
7. and the public attestation matches the expected collection root.

## 13. Public and Private Data Boundaries

PRS-001 separates public verification data from private or licensed reproducibility data.

### Public Data

Public proof data may include:

- asset name,
- asset URI,
- metadata URI,
- SHA-256 anchor hash,
- leading-zero bit count,
- rarity class,
- odds estimate,
- Merkle leaf,
- Merkle proof,
- collection root,
- verification result.

### Private or Licensed Data

Private or licensed data may include:

- seed,
- preimage,
- nonce,
- timestamp,
- mining session logs,
- deterministic generation parameters,
- reproduction secrets,
- private hash inventory,
- unrevealed collection manifests.

This allows an asset to be publicly verifiable without exposing private entropy sources or premium reproducibility data.

## 14. Open Standard Commitment

PRS-001 is intended to be an open standard.

The following components are intended to be public:

- rarity ladder,
- anchor object format,
- proof object format,
- metadata schema,
- Merkle leaf construction,
- single-root collection proof method,
- verification procedure,
- reference verifier,
- example low-rarity anchors,
- developer documentation.

The following components may remain private, licensed, or commercially protected:

- rare unused hash inventory,
- private seed data,
- preimages,
- nonce logs,
- mining session logs,
- deterministic generation parameters,
- premium reproduction engines,
- unrevealed collection manifests,
- advanced commercial APIs.

The goal is to make the standard easy to adopt while preserving the value of scarce cryptographic inventory and advanced creation systems.

## 17. Security Considerations

PRS-001 public verification depends on:

1. correct SHA-256 digest formatting,
2. accurate leading-zero bit calculation,
3. deterministic proof object canonicalization,
4. correct Merkle proof generation,
5. secure storage of private seeds and preimages,
6. prevention of duplicate anchor licensing,
7. transparent distinction between public proof data and private reproducibility data.

Implementers should not publicly expose private seed, preimage, nonce, or mining session data unless intentional.
